# JEV build: tracks, ownership, and what exists today

The build plan for [docs/jev.md](../jev.md). Seven tracks build it: foundation, then six feature tracks in parallel that do not talk to each other. Every line reference is to commit `09a1c045f` on `multi-account-orchestrator` unless another branch is named; after the foundation merges, find a region by the function named beside it, not by the number.

The decisions D1–D8 are in [docs/jev.md](../jev.md#decisions), numbered as in `~/bozeo-ops/jev-build-state.md`. Build to them; they are not open.

## File ownership

Every file any track creates or edits has one owner among the tracks that run at the same time. A track that needs a change in a file it does not own asks the orchestrator; it does not make the change. Test files belong to the owner of the file they test.

The foundation merges before any feature track starts, so a foundation edit inside a region a feature track owns later (the two factory inputs in `bootstrap.ts`, `EpisodeSchema`) is sequential, never a merge conflict.

## Dependency graph and merge order

```text
design ──► foundation ──┬──► classifier (2)
                        ├──► remediation (3a, 3b)
                        ├──► stalls (10)
                        ├──► tools (4–6) ◄ · · catastrophe-gate (feature 1), by interface only
                        ├──► ui (11)
                        └──► compaction (9), last; dormant until leader compaction is on
```

- No feature track depends on another. Each records decisions through `jev.decisions`, the foundation's store, so they appear in the UI the moment ui merges, in any order.
- **stalls and remediation.** stalls sets `escalation.personFirst`; remediation honours it. The field is the foundation's, so either can merge first: until remediation merges, the ladder ignores the field and starts the agent, which is today's behaviour.
- **tools and the catastrophe gate.** tools codes against `CommandGate` in `jev/contract.ts`. If the gate has merged, tools adapts `checkCatastrophe` in bootstrap. If not, tools merges with `command` refused ("command needs the catastrophe gate; run it with Bash"), and whichever of the two merges second adds the adapter, about ten lines in the tool host dependency region. The gate branch also edits `paseo-tools.ts` (`gateTerminalInput`, `:585-615` on that branch), in a different hunk from the tools registration.

Merge order after the foundation: classifier, remediation, stalls, tools, ui, then compaction.

- classifier touches only plugin files, so it cannot conflict.
- remediation and stalls both touch `docs/remediation.md`, in different hunks; stalls rebases on remediation.
- tools goes after the catastrophe gate when it can.
- compaction is built last because feature 9 does nothing until Tyler enables `agents.leaderCompaction`.

Each track rebases on the integration branch before its adversarial review and again before merge. Run at most four at once while the machine is loaded.

**The install track.** `.claude/commands/install.md` on `multi-account-orchestrator-agentic-install` does not check for a JEV key today. If it adds one, it checks `PASEO_JEV_API_KEY` in `~/.config/paseo/jev.env`, never `OPENROUTER_API_KEY`.
