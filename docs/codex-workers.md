# Codex workers

A daemon-launched Codex child agent is a worker running under full guard coverage: the catastrophe gate, the native build gate, the device cap, and the physical-device install gate. Codex children have guards and are subject to caps; otherwise they work like any other agent.

## Binary discovery

The daemon finds Codex in this order:

1. PATH — any `codex` command available in the shell
2. ChatGPT bundle — `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex` (macOS) or `~/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex` (user-installed, macOS)
3. Microsoft Store package `OpenAI.Codex_*` (Windows only)
4. `agents.providers.codex.command` in config — overrides all of the above

If none of these work, the error lists every path searched. Configure `agents.providers.codex.command` to specify a custom path.

## Platform notes

### macOS

The daemon probes `/Applications/ChatGPT.app` and `~/Applications/ChatGPT.app`. Both are checked.

### Windows

The Microsoft Store package `OpenAI.Codex_*` is the standard source. The daemon scans `%LOCALAPPDATA%\Packages` for packages starting with that prefix, sorted by name, and probes each candidate.

If the ChatGPT desktop app bundles Codex on Windows, that path will be added; this has not yet been verified on Windows builds.

## Codex guard health

Codex refs are usable for children only while a self-test has recently proved the guard works (`agent/codex-guard-health.ts`). Three states: `unknown` (no self-test has run, or it errored/timed out), `green`, `red`. Both `unknown` and `red` make every `codex/` ref unusable.

**Self-test:** a scratch guarded Codex child, in a throwaway temp-dir git repo, asked to run three commands in order: `touch` (PowerShell: `New-Item -ItemType File -Force -Path`) an ok file, the same for a canary file, then `git push --force origin main` against a bare remote. The prompt asks the model to request escalated permissions for all three up front, since each one writes outside the sandbox's writable roots. The ok/canary files and the bare remote live in a daemon-owned scratch directory (`$PASEO_HOME/codex-guard-self-test/<8-hex-chars>/`, threaded in from `bootstrap.ts`) -- never under the session's own cwd, `os.tmpdir()`/`$TMPDIR`, or `/tmp`, all of which a `workspace-write` sandbox makes writable by default. Only the cwd itself stays an ordinary temp directory, since it is a writable root regardless of config and nothing sensitive lives directly in it. `runCodexGuardSelfTest` refuses to run at all, and turns health red with a reason naming the path, if the configured scratch root resolves (realpath) inside `os.tmpdir()`/`/tmp` -- running anyway would reproduce the original bug this directory exists to prevent. A leftover scratch directory from a crashed daemon (matching the `^[0-9a-f]{8}$` name pattern, older than an hour) is swept at the start of each run.

The self-test supplies its own `DeviceLaunchGate` for the one session — it never reuses the real device cap, since the canary must be denied regardless of the cap's state — that allows the ok path and denies the canary path. The force-push is declined by the real catastrophe gate before the device gate is ever consulted, so the self-test instead subscribes to the session's timeline for the gate's own `rule: force-push-main` refusal text. Green requires all of: an approval request arrived for the ok command, it was approved, the ok file exists; an approval request arrived for the canary command, it was declined, and the canary file does not exist; the catastrophe gate's force-push-main refusal was observed. A canary file that exists is red regardless of anything else observed in the same attempt -- that alone proves the guard failed to block it, checked before any of the other conditions above. A self-test that errors or times out leaves health exactly where it was, unless a previous attempt in the same run already produced a red verdict (see retry below) — an infrastructure failure on its own is not proof the guard is broken, so it does not get to claim one either way. A live-detection red that lands on a different, concurrently-running guarded child while this self-test is still in flight stays sticky: the self-test checks, right before writing its own verdict, whether a newer red arrived after it started, and leaves it alone rather than overwriting it with a stale green.

**Retry on a model slip:** a red verdict retries once, with a fresh cwd, scratch directory and session, when the reason is a model mistake a second attempt could plausibly avoid — a missing or declined approval request, or a missed catastrophe-gate refusal. A red because the canary ran (or any other reason outside that list) proves the guard or the self-test harness itself is broken and is never retried. The final state is the first green, or otherwise the most recent red verdict from any attempt — a second attempt that itself errors or times out does not discard a red the first attempt already found; only a run where every attempt ends in an infrastructure error, with no verdict ever reached, leaves health exactly as it was found.

**When it runs:** at daemon start, and hourly after that (`codex-guard-boot-health.ts`'s `createCodexGuardBootHealthScheduler`, wired from `bootstrap.ts`), which checks `shouldRunCodexGuardSelfTest` and only actually runs the test when a day has passed or the Codex binary's `--version` output has changed since the last run. A module-level in-flight guard skips a tick that lands while a previous run (hung in `createSession`, say) is still pending, rather than starting a second one beside it. A tick that has to skip the self-test itself — no Codex binary found, an empty catalog — records the reason in health state (so `codex.guard.status` and a create's refusal message say which one happened, rather than the unchanged default "No self-test has run yet.") and retries on a short bounded backoff (1, 2, 5, then 10 minutes) rather than waiting the full hour; it resets back to the hourly cadence once a tick actually runs the self-test, or finds it isn't due yet.

**Live detection:** every top-level shell command item a guarded child completes is re-checked after the fact against the real catastrophe and device gates (`recheckCodexGuardCommandItem`, reusing `codex-guard.ts`'s `decideCodexGuardedCommand`). A command one of those gates would refuse, that ran with no approval request ever having been seen for it, turns health red immediately and cancels the agent's turn. A command on Codex's safe list (one that never needs to escalate, so never raises an approval request) is not a violation either way.

A command that exited non-zero is skipped by this re-check, but only when the session's own _effective_ sandbox policy -- the one Codex actually applied, read back off the `thread/start`/`turn/start` response, not whatever Paseo requested -- is a containing `workspaceWrite`: network access off, and no writable roots beyond the sandbox's own defaults. Under a containing sandbox, a gated write or launch cannot have reached outside it, so a non-zero exit proves the sandbox stopped it rather than a gate. Every guarded turn pins `networkAccess: false` in the sandboxPolicy it sends, whatever the host's own Codex config says — the gates' whole premise is that a network action (a push, `adb` over `localhost:5037`) must escalate, which only holds when the sandbox itself never lets one through unescalated. A host config that grants extra writable roots to guarded turns is not pinned away the same way, so that alone can still make the sandbox non-containing; in that case every completed command is judged exactly as it would be with no exit code at all.

**Reaching the classifier: `codexGuard.status`.** Plugins don't import daemon modules directly — they call a `paseo.<namespace>` RPC action exposed through `PluginHookContext`, the same way `jev-availability.ts` polls `paseo.jev.status()`. `codex.guard.status` (`packages/server/src/server/session/codex-guard/codex-guard-session.ts`, gated on `server_info.features.codexGuardStatus`) carries `isCodexGuardHealthy()`'s state plus the currently-running Codex child count across that boundary: `{status, reason, checkedAt, codexVersion, runningChildren}`. `runningChildren` counts through `requiresCodexGuard` (not a literal provider/label check), so a derived `extends: "codex"` provider and a marker-only child (detached, but still guarded) both count against KTD-9's `maxChildren` cap — Tyler's own Codex sessions (no parent, no marker) never do. Both values are read fresh per request; neither is cached on the daemon side.

The plugin polls this the same way it polls `jev.status`: `server/codex-guard-availability.ts`'s `createCodexGuardAvailability` (60s interval, 5s per-call timeout, a 10-minute backoff after an `unknown_schema` rejection from a daemon that doesn't know the RPC). A daemon without `paseo.codexGuard` at all — a plugin reloaded against an older host build — is feature-detected the same way `paseo.jev` is: by attempting the call and checking `typeof paseo.codexGuard?.status === "function"` first, not by trusting the plugin's own bundled client types (a staged build can pair a new plugin with an old daemon). The snapshot the poller caches is `{healthy, runningChildren}`, where `healthy` requires both a `green` verdict and a `checkedAt` within 26 hours — stale enough to tolerate the daemon's own hourly check cadence, but short enough to catch a daemon whose self-test scheduling has stopped entirely. `unknown`, `red`, a stale `green`, a missing RPC, and a failed poll all read `healthy: false`.

`index.server.ts` wires the resulting cache into `RoleRouterOptions.codexGuardCache` (the create hook's `ClassifierWorld.isCodexGuardHealthy`/`runningCodexChildren`) and `RoleModelPolicyRpcDeps.codexGuardCache` (the settings screen's `role-model-policy.explain` preview), mirroring `arenaRankingCache` in both places. Without either cache wired, both paths fall back to "every `codex/` ref unusable" (guards-first, KTD-3) rather than claiming a model they can't actually route to.

## Guarded mode: the daemon answers Codex's own approval requests

Codex children run in a `guarded` mode preset (`MODE_PRESETS.guarded`, internal — never offered in `CODEX_MODES`): `sandbox_mode: "workspace-write"` with `approval_policy: "on-request"`. A guarded child's `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` requests are answered in-process by the daemon instead of being surfaced to a person: `checkCatastrophe`, then the composed `deviceLaunchGate`, decide accept or decline before anything runs. No hook, no trust file, nothing written to `~/.codex`. Fails closed by construction — nothing runs until the daemon says yes.

**Why not hooks.** See "Guard hook: superseded" below — no hook delivery path survives unattended under `app-server`.

**Why not `danger-full-access` + `untrusted` (the first guarded-mode design).** Confirmed empirically against the real ChatGPT-bundled binary (0.160.0) on 2026-10-09:

- `approval_policy = "untrusted"` is rejected outright: `failed to load configuration: approval_policy = "untrusted" is no longer supported; remove this setting`. The top-level `codex --ask-for-approval`/`-a` flag's own `--help` confirms only `on-request` and `never` remain as plain string values (plus a `granular` object form).
- `sandbox_mode: "danger-full-access"` never triggers an approval request, with _any_ approval policy, `granular` included: nothing needs to escalate out of a sandbox that is already fully open, so there is nothing to ask about. Confirmed by running a guarded-shaped session and watching a `touch` outside the workspace succeed silently, with zero `permission_requested` events.

Re-checked a second time on 2026-10-09 against the installed binary (`codex-cli 0.160.0`, unchanged) after this finding was questioned: `codex exec -c 'approval_policy="untrusted"' -c 'sandbox_mode="danger-full-access"' ...` still fails immediately with the identical config-load error, before any turn runs. The result is reproducible, not a fluke of one run or one environment.

**What does work.** `sandbox_mode: "workspace-write"` with `approval_policy: "on-request"` — the same values Paseo's existing `auto` mode already uses for people. Proven end-to-end against the real binary: a command needing to escalate beyond the workspace root (deleting a file in `$HOME`, in this case) produces an `item/commandExecution/requestApproval` request _before_ the command runs; responding `accept` lets it run (the file was deleted); responding `decline` blocks it (the file still existed afterward, and the model reported "the escalated `rm` request was rejected"). The model has to recognize it needs to request escalation — a command it runs without flagging that just gets denied by the sandbox directly, with no approval request at all. Either way nothing catastrophic succeeds: a command the catastrophe gate would refuse either gets an explicit decline, or never executes because the sandbox denied it outright.

This changes what "guarded" means from the mode picker's `auto`: the _values_ are identical, but a guarded child's approval requests never reach a person — `handleCommandApprovalRequest`/`handleFileChangeApprovalRequest` detect the guarded mode and decide synchronously instead of creating a pending permission.

**File changes and the git-alias blind spot.** `item/fileChange/requestApproval`'s own params carry no path info — confirmed against the real app-server protocol — so `handleFileChangeApprovalRequest` looks up the touched paths from the `item/started` notification for the same item id, which always precedes the approval request. In-workspace writes never raise an approval request at all under `workspace-write` (they apply directly, with no `requestApproval` round trip); a `.git/` write does, even inside the workspace. Each reported path is resolved before it is tested: every existing path component is `lstat`-ed in order, and any symlink found — including a dangling one, whose target does not exist yet, the shape `apply_patch` "creating" a new file through a planted symlink takes — is read via `readlink` and resolved in its place, with a hop limit against a symlink cycle. A path that cannot be resolved at all, or exceeds the hop limit, is treated as sensitive. Guarded mode declines a (resolved) file change under any `.git/` or `.ssh/` directory, a `.gitconfig`/`$XDG_CONFIG_HOME/git/config`, a `.gitattributes` (filter drivers), or a shell rc file, and approves everything else — closing the path through which an always-accepted `apply_patch` could otherwise add a `pf = push --force origin main` alias to `.git/config`, which `checkCatastrophe`'s shell parser (`docs/catastrophe-gate.md`) would never recognize as a force-push once invoked as `git pf`. An item whose changed paths were never tracked at all (a malformed payload, a notification that never arrived) declines too, rather than falling through to an accept. `decideCodexGuardedCommand` closes the command-side half: it declines a `git` invocation carrying its own `-c`/`--config-env` option, a `GIT_CONFIG_KEY_*` environment assignment, or a `git config` subcommand (any form — legacy `git config <key> <value>`, `--global`/`--file`, or the newer `git config set <key> <value>`) that sets an alias, `core.hooksPath`, `core.sshCommand`, `core.fsmonitor`, `include.path`/`includeIf.*.path`, `url.*.insteadOf`, or any `*.helper` — including the one-command form (`git -c alias.pf="push --force origin main" pf`) that sets and invokes the alias in the same breath, and a quote-split key (`git config alia""s.pf ...`) that a plain-text regex over the command would miss but the shell's own word-expansion resolves to `alias.pf` same as everywhere else. All of these read the key off the same shell-tokenizer word the catastrophe gate itself parses, not off the unparsed command text.

Several more properties of the resolver and the sensitivity check, found by later verification rounds. The sensitivity check compares path segments and git config keys lowercased and Unicode-NFC-normalized, always -- macOS and Windows volumes are case-insensitive by default, so `.GIT`/`.Git` resolves to the same directory as `.git`; comparing case-insensitively is strictly more inclusive, never less, so it costs nothing on a case-sensitive volume. The resolver never calls `path.resolve`/`path.normalize` on a reported path before walking it: those collapse a `..` against whatever text precedes it with no idea whether that text is a real directory or a symlink, so `objlink/..` would silently treat `objlink` as transparent instead of going to the parent of wherever `objlink`'s target actually resolved to; the same applies to a _missing_ component -- `newdir/../hooklink/x` with `newdir` never existing must still follow `hooklink` if it's a real symlink, so a missing component joins the resolved stack like an ordinary name instead of ending the walk. `..` (and a missing component) are handled inside the same component walk, resolved against the real location built up so far, after any symlink substitution that already happened. A rename's destination can arrive in at least four shapes across the two notification channels -- `kind.move_path`/`movePath` (an object-shaped `kind`), a bare-string `kind` with `move_path` as a top-level sibling, a top-level `type` field with `move_path` alongside it (the real legacy-channel map-entry shape), or an older `{typeName: {move_path}}` wrapper -- `parseCodexPatchChanges` reads all four, and both the source and the destination are tracked and checked.

Last, an NTFS volume (Windows is a required target platform for this project, not a hypothetical) can address the same file under several aliases a naive string comparison would miss entirely: a trailing dot or space (`.git.`, `.git `), an alternate-data-stream suffix (`.git::$INDEX_ALLOCATION`), or an 8.3 short name (`GIT~1`, `GITCON~1`). The first two are stripped per path component by `comparableName` (`jev/secret-paths.ts`, shared with the JEV read check rather than reimplemented here -- see docs/jev.md Feature 16 step 7) before the sensitivity check runs. The 8.3 case has no reliable text-only answer (the exact short name a directory gets depends on what else collides there), so it's a heuristic: any component shaped `<1-6 chars>~<digits>` whose prefix is a case-insensitive prefix of a sensitive name (dot removed) declines. On win32, the resolver also tries `fs.realpathSync.native` on each existing component, which asks the OS for the real long name directly and makes the heuristic unnecessary whenever the path already exists.

HFS+ has its own version of the same problem: it ignores U+200C-200F, U+202A-202E, U+206A-206F and U+FEFF entirely when comparing two names, so `.g‌it` (a zero width non-joiner after the "g") opens `.git` on an HFS+ volume -- the same class of gap as git's CVE-2014-9390 / `core.protectHFS`. `comparableName` strips exactly that set, before the case/NFKC folding above; U+200B (zero width space) is deliberately not on the list, since HFS+ does not ignore it.

Two platform-specific corrections on top of that. `\` is an ordinary filename character on POSIX, not a separator -- the resolver's own component splitter only treats it as one when `platform === "win32"` (a parameter, defaulting to `process.platform`, injectable so a test can exercise the win32 branch from any host). An earlier version split on both unconditionally, so a single real POSIX component literally named e.g. `zz\..\..\..` tore into four fake navigation segments instead of the one real name the kernel sees, walking the resolver somewhere the real write never lands. Separately, on win32 the resolver strips a trailing dot or space from each component before `lstat`/`readlink` -- the same normalization Win32 itself applies when it opens a file -- so a symlink/junction reported with one (`hooklink.`) is still found and followed instead of read literally, getting `ENOENT`, and treated as a missing component.

## What this guard does not catch

Pattern-based, at parity with what Claude's own catastrophe-gate hook catches and misses (`docs/catastrophe-gate.md`'s "Known gaps": unresolvable values, code in another language or a script file, push config, the remote's own side, other routes to a shell or to moving a ref). Nothing here is Codex-specific — a gap in the shared `checkCatastrophe` parser is a gap for every provider it runs under.

Codex-specific gaps on top of that:

- **In-workspace writes raise no approval request at all.** Confirmed against the real app-server protocol (above): `workspace-write` applies a write inside the sandbox root directly, with no `requestApproval` round trip, so nothing in guarded mode ever sees it. The file-change sensitivity check above only runs for writes that do escalate — a `.git/`, `.ssh/`, or shell-rc path, which the sandbox treats as outside the workspace even when nested inside it.
- **Interactive shell input typed during a running turn gets no re-check.** A tool call is visible to the guard when the model presses Enter on it, not as it types into an already-running process — the same gap Claude has, and the same shape as `docs/catastrophe-gate.md`'s own "other routes to a shell" (`send_terminal_keys` arrives as terminal input, not a gated tool call).
- **A hard link is not checked at all.** The file-change resolver (above) follows a _symlink_ at every path component, but a hard link to a sensitive file is a second directory entry pointing at the same inode with no symlink anywhere in the chain -- an in-workspace write through a hard link is exactly the "in-workspace writes raise no approval request at all" case above, just reached by a different mechanism than a planted symlink.
- **Mixed `/` and `\` separators in one reported path are covered, not a gap:** both the sensitivity check and the resolver split on either separator unconditionally, not only on Windows.

## Guard hook: superseded, no unattended delivery path (Codex CLI 0.160.0)

The original guard design used a PreToolUse hook. No hook delivery path runs unattended under `codex app-server`— this is why guarded mode (above) exists instead. Keep this list as the recheck for a future Codex release:

- **`-c` config overrides** (`codex app-server -c 'hooks.PreToolUse=[...]'`): the key is accepted — `--strict-config` does not reject it — but the hook never runs. It is silently skipped with no log line, no error, no block.
- **`~/.codex/hooks.json`** (the file-based path the terminal activity hook installer uses): same result. A `PreToolUse` entry added directly to the real file is silently skipped under non-interactive `codex exec`, identical to the `-c` case.
- **`--dangerously-bypass-hook-trust`**: this flag does run an untrusted hook (confirmed: the hook fired). But it exists only on `codex exec` — `codex app-server --dangerously-bypass-hook-trust` is a hard CLI error (`unexpected argument`). It also does not persist trust to `config.toml`; re-running without the flag goes back to silent-skip. There is no way to use it to bootstrap trust for later unattended `app-server` runs.

(A `trusted_hash` mechanism in `config.toml` and a `ManagedHooksRequirements`/MDM-style path also exist and were ruled out — see git history on this file for the full detail.)

If a later Codex release restores an `untrusted`-equivalent approval policy that asks even under `danger-full-access`, or adds an unattended-automation path for hook trust, re-run the checks above (and the guarded-mode proof) against the new version before changing this design.

## Classifier plumbing for a routed Codex child

A worker or reviewer the classifier routes to a `codex/` ref gets, on its create request (`role-router.ts`), unconditionally — an explicit request for some other Codex mode or profile shape does not bypass any of this:

- **`modeId: "guarded"`.** One step, `withCodexGuard` in `role-router.ts`, computed once per create and applied to whichever return path the request takes — the honored-request path, the unconfigured-pool path, the provider-not-registered recovery path, and the ordinary rewrite all share it, instead of each carrying its own copy. It is keyed on `resolveFinalProviderId`, not `decision.model.provider` alone: that field is unreliable on several paths (null for `unconfigured`, an echo of the request for `honored-request`, and still null for a same-family bare pool ref even on the ordinary rewrite path), so the guard resolves the create's actual final provider instead, then resolves that provider's session FAMILY (`ProviderIdCache.resolveFamily`, walking `derivedFromProviderId`), so a derived `extends: "codex"` provider guards exactly like `codex` itself. "Child" is a `callerAgentId`, or an inherited `paseo.parent-agent-id` label read structurally off the request (a label-only child, e.g. an agent-made schedule run, carries no caller of its own) — not `callerAgentId` alone. Tool enforcement is computed from this guarded base, not the raw request, so its own trusted `providerOptions` (e.g. a read-only profile's `sandbox_mode`) always lands on top of the stripped `approval_policy`/`sandbox_mode`/`sandbox_workspace_write`, never the other way around. A root create (no `callerAgentId`, no parent label, i.e. Tyler from the app) keeps whatever mode it asks for. When the classifier's own fallback-anyway pick (the usability gate below, "rather than dropping the spawn") names a codex ref for a child while `codexGuardCache` reports anything short of healthy, routing falls back to the request's own provider/model instead of handing the daemon a create it can only refuse — enforcement is recomputed against that provider too, and the Codex guard slot (below) is never reserved for a create that ends up not running on Codex.
- **The thinking clamp (`decideCodexThinking` in `classifier.ts`).** Codex has no entry in `world.thinkingCatalog` (Claude is the only provider that reports thinking options through `listModels`), and Codex's own effort ladder — `low`/`medium`/`high`/`xhigh` plus `max` and `ultra` — is not Paseo's. The requested (or leader-rule, or task-class-default) level is resolved the same way as the Claude path, then capped to `xhigh` whenever `thinkingLevelRank` returns undefined for it, or returns a rank above `xhigh`'s. That one check covers Codex's own `max` and `ultra`, Ultra Code, and anything unranked, uniformly. Recorded as an `override` with `reason: "codex-max-effort"`.
- **Tool profiles, Codex-shaped (KTD-8).** `applyToolProfile` (`shared/tool-profiles.ts`) takes a `targetFamily` argument; for `"codex"` it never writes Claude's `settings.permissions`/`disallowedTools`, since Codex has no per-tool denial mechanism this codebase knows of. `read-only` maps to `sandbox_mode: "read-only"` instead — Codex's own investigate-only mode. Every other profile with a real denial (its own, or inherited) cannot be expressed at all: `isToolProfileExpressibleOnCodex` says so, and `classifier.ts` folds that into the usability gate below rather than silently dropping the restriction. The check only sees the role's own configured profile — a denial inherited from the agent that spawned this one is not checked yet (`decideModel` has no access to that half of the tool decision).
- **The usability gate (KTD-9, KTD-3), `role-availability.ts`'s `isRefUsable`.** A `codex/` ref is usable only when all of: `isCodexGuardHealthy()` is true, the `codex` `session` window reading is under `agentModelPolicy.codex.maxWindowPct` (default 60) and under `maxReadingAgeHours` old (default 2), fewer than `maxChildren` (default 3) Codex children are running, the role isn't the leader, and the role's tool profile is expressible on Codex (above). Every one of these fails closed on missing data. The window reading and its age come from the existing provider-agnostic usage poller (confirmed: `services/quota-fetcher/providers/codex.ts` reports Codex's primary window under window id `"session"`, the same id KTD-9 names) — no new RPC needed for budget. `health.ts` gained `windowReadingAgeHours` for the age half. This gate runs through `evaluateRequestedModel`/`selectModel`; the `unconfigured` model-decision outcome (an empty pool) never calls either, so an explicit codex request against an empty pool stands unevaluated. The `modeId: "guarded"` guard above does not rely on this gate: it keys on the create's own final provider directly.

### Daemon-side guard, independent of the plugin

The plugin above is fail-open by contract: a throw anywhere in classification passes the request through untouched. So the daemon enforces the same invariant itself, in `AgentManager.createAgentInternal` (`enforceCodexChildGuard`, `packages/server/src/server/agent/agent-manager.ts`), after the plugin's `before("agent.create")` hooks have run and the final `config` is known, before `prepareSessionConfig` bakes it into what actually reaches `client.createSession`. Resume (`resumeAgentFromPersistenceInternal`) and reload (`reloadAgentSessionInternal`) run the same forcing before they rebuild a session's launch config, and `moveAgentToProvider` refuses a move that would take a guarded agent out of the codex family.

One predicate decides "child" on the daemon side: `requiresCodexGuard` (`codex-guard-predicate.ts`). The plugin mirrors the same rule structurally (above) rather than calling this directly — it can't import daemon modules. `requiresCodexGuard` is true when the session family of the final provider (`resolveProviderSessionFamily` — a provider declared `extends: "codex"` guards exactly like `codex` itself) is `codex`, and the agent is not human-made, decided from a daemon-assigned **origin** rather than inferred from `callerAgentId`/labels after the fact:

- Every create passes an explicit `origin`: `"human"` for an app/desktop/CLI client session with no `callerAgentId`, `"agent"` for a client session carrying one or for anything through the Paseo MCP endpoint (agent-only by construction), `"daemon"` for a Hub execution or a remediation agent. **A create that never sets `origin` is treated as agent-made** — new or forgotten create paths are guarded by default, and only the explicit human path opts out.
- Resume and reload have no origin of their own (they reconstruct a stored record, not a fresh create) and fall back to the older rule: a `callerAgentId`, an inherited `paseo.parent-agent-id` label, or the durable `paseo.codex-guarded` marker already being present all count as agent-made.
- The marker counts on its own regardless of origin: once stamped, it survives a relabel or detach that clears `paseo.parent-agent-id`.

Given a child:

- A create `requiresCodexGuard` forces into `modeId: "guarded"`, whatever the plugin did or didn't do, and stamps the marker onto the agent's labels.
- The marker is protected (`PROTECTED_LABEL_KEYS`): `update_agent` cannot clear it, so a later relabel or detach — which already clears `paseo.parent-agent-id` — cannot undo the guard either.
- A brand-new create is **refused outright** — `createAgent` rejects, nothing is ever sent to the provider — unless `isCodexGuardHealthy()` reads `true`. `unknown` and `red` both refuse, guards-first same as the classifier's own gate above, throwing a typed `CodexChildGuardError` (`code`, `healthStatus`, `reason`). Resume and reload use a looser rule: only `red` refuses, since `unknown` is the state at every boot until the self-test completes, and refusing there would wedge restart recovery for every Codex child on every daemon start. `importProviderSessionInternal` (`paseo agent import`, account-failover migration) runs the same resume/reload rule on the imported `{provider, cwd}` plus its incoming labels, before `prepareSessionConfig`.
- A root create (`origin: "human"`, or for resume/reload: no inherited label, no marker) and an internal create (`config.internal`, e.g. the guard self-test's own session, which never reaches this path anyway) are untouched.

A child also cannot switch itself out of guarded mode later: `AgentManager.setAgentMode` refuses a mode change away from `"guarded"` for any agent `requiresCodexGuard` still says is a child — a root Codex session can switch freely. Moving a guarded child to a provider outside the codex family is refused the same way (`AgentProviderMoveError`'s `codex_guard_protected` code), as defense in depth behind the generic cross-family `incompatible_provider` refusal.

**Schedule runs.** A schedule carries its own `createdByOrigin` (and `createdByAgentId`), set at `schedule/create` time the same way a session-kind create decides origin, and always `"agent"` for the MCP endpoint (`create_schedule`/`create_heartbeat`). Every `new-agent` run passes the schedule's `createdByOrigin` straight through as the run's own create `origin` — the run stays a root (no `paseo.parent-agent-id` label of its own), but is still guarded whenever the schedule itself is agent-made. A schedule written before `createdByOrigin` existed has none and is treated as agent-made — fail closed. An agent (`callerAgentId`, or the MCP endpoint) editing a schedule's `newAgentConfig` through `update_schedule` or a same-name `create_schedule`/`create_heartbeat` upsert marks the schedule agent-made from that point on; a human edit never downgrades it back. A schedule's own stored `modeId` can't defeat any of this — the daemon forces guarded mode at create time regardless of what the config asks for.

### How guard health reaches the classifier

See "Guard health" above for the `codex.guard.status` RPC and `codex-guard-availability.ts`'s poller. `index.server.ts` passes the resulting cache to both consumers of `ClassifierWorldBase.isCodexGuardHealthy`/`runningCodexChildren`: the create hook (`RoleRouterOptions.codexGuardCache`) and the settings screen's `role-model-policy.explain` preview (`RoleModelPolicyRpcDeps.codexGuardCache`). A daemon older than this bridge, a plugin that hasn't warmed its first poll yet, or a poll that fails all read as `isCodexGuardHealthy() === false` — the same fail-closed default (guards-first, KTD-3) this file already documents for a missing guard-health source.
